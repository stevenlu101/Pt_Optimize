# 搜形状：把锥形舌片与孔族接进搜索空间（R38）

## 背景

用户 2026-09-10 晚工单第 2 条原话：「搜形状不搜锥形与孔族，只搜盘径／舌宽」——这是之前排查
（`deliverable/功能落地排查_2026-09-11_R18-R34.md`）里列出的未完成项，用户点名要做。

用户 2026-09-11 确认的目标原话：「结果就是一次搜完，工程师看到每一族最轻的可行形状，以及锥形
有没有帮助，不用手动改勾选反复跑 <-- 这是我要的」。

在这条工单之前，「◇ 搜形状」只搜盘半径与舌宽比例这两维：锥形舌片（R31，用户「拍脑袋」画的侧
Y 形）与孔族（R32，不挖舌孔／挖舌孔两族独立求优、不比重量）虽然都已经落进 `DesignSpec` 与
`Solver`，但工程师要用它们，得自己在①页勾/切，再手动点一次「搜形状」，改一个变量重跑一趟——
锥形有没有帮助、哪一族更轻，全靠工程师自己多跑几趟去比，APP 没有替他把这件事一次做完。

## 改了什么

### 0. 先补齐 R36（并行化）

worktree 分支的基线（1ccfc0d）里没有 R36「搜形状并行化」——主树已经合入但还没提交到这条分支。
按工单第 0 步从主树复制了 `Core/ShapeBatchEval.cs`、`UI/LineDesignPage.cs`、
`Pt_Optimize.Tests/ShapeBatchEvalTests.cs`、`ShapeSearchParallelTests.cs`、`HANDOVER.md` 五个文件，
`dotnet build -c Release` confirm 0 错误后才开始本次改动。`Core/ShapeBatchEval.cs` 全程未动——
它是 R36 的并行核心（`SemaphoreSlim` 限流、结果按输入下标装回、取消时已完成的不丢），本次只是
在它上面多喂了一维（锥形）和多跑了一遍（孔族）。

### 1. 锥形舌片进搜索空间——`Core/ShapeSearchPlan.cs`

新增三组**重载**（旧签名原样保留，行为逐位不变，新的一套只是多带一个 `bool taper`）：

- `Neighbours(R0, hw0, taper0[, stepMm])` —— 给 **5 个邻点**：前 4 个与旧的 4 邻点算法完全一样
  （盘径 ±步长、舌宽比例 ±步长，锥形不动），第 5 个是「原地不动、翻转锥形」。
- `Key(R, halfW, taper)` —— 去重键把锥形也写进去：平行边与锥形边是两个不同的候选，不能因为
  盘径/舌宽相同就被判成「已经算过」而互相顶掉。
- `Worth(cand, seen[, minDiscMm])` —— 带锥形的候选过滤重载，走新的三参数 `Key`。

理论依据（写进了 `ShapeSearchPlan.cs` 的 XML 注释里，不是拍脑袋多加一维）：锥形舌根按切线自动
变宽 ⇒ 舌根截面积比平行边大 ⇒ 按 J = 电流/截面积 定厚时，舌根可以更薄、叉臂可以更短——这是省
的一边；但舌片展开面积也比平行边大（两侧多出一块三角形），这是费的一边。**两头拉，谁赢只能算
出来比，不能拍**——这正是把「要不要锥形」当成搜索维度、跟盘径/舌宽用同一套导航网格 + 邻域探索
决定的理由。

只在**邻域探索**（⑦，`SearchShapeAsync` 里那五个方向）里出现「翻转锥形」这一个方向：第 1 轮网
格、不动点迭代（②）、二分（③）、黄金分割（④）仍然按进入搜索时那一个锥形值（来自①页当前勾选）
跑——那几步找的是盘径与舌宽，不该同时又变出第三维，把「盘径变化」的贡献跟「锥形变化」的贡献搅
在一起看不清。等邻域探索把方向摸出来了，锥形才跟着盘径/舌宽一起被局部搜，与它们共用同一套「步
长收缩、没有更好就收窄」的停机逻辑。

`UI/LineDesignPage.cs`：`SearchShapeAsync` 里 `rows`/`seen`/`EvalShapesBatch` 的候选都带上
`Taper`，构造 `DesignSpec` 时 `seed.TabTaper = 候选.Taper`（不是照抄页面当前勾选）；胜出者的锥
形写回 `_tabTaper.Checked`——与写回盘径/舌宽/舌长在**同一处**、被**同一个** `_suppressAuto`
包裹；输出表多一列「舌边」（平行／锥形）；`ShapeRowText`（下拉条目）也带「锥形」字样，让工程师
在「搜形状结果 ▾」里一眼看出哪个候选是锥形。

**顺手抓到并补上**：`PickShape()`（工程师在下拉里选一个形状写回页面，它自己的文档注释写着「与
搜形状写回赢家同一条路」）原来没写 `_tabTaper.Checked`——下拉条目现在会说「锥形」，选中之后勾选
框却不跟着变，正是「新状态位没接到下游」那一类老毛病（同一位已经栽过不止一次）。已经补上，同一
个 `_suppressAuto` 块里。

### 2. 孔族（不挖舌孔／挖舌孔）——同一份搜索主体，两族各跑一遍

① 页「解法」= 两个都算 时，把 `SearchShapeAsync` 原来那一整段搜索逻辑（网格 → 不动点 → 二分 →
黄金分割 → ⑥ 剩余舌宽比例 → ⑦ 邻域探索 → ⑧ 精算）抽成局部函数
`SearchOneFamilyAsync(bool allowCuts, string famTag, string famPrefix, string? famProvTag, rows)`
（**只写一份**，不是复制两份改一份——那是本项目「同一件事写两遍、改一处忘一处」最典型的病灶）：

- 先跑一遍 `allowCuts=false`（不挖舌孔族），再跑一遍 `allowCuts=true`（挖舌孔族）——两族各自独
  立选最轻可行的形状，**不比重量**（R32 原则在搜形状里也要成立，用户 09-10「R23 与 R29 不比较
  重量」的原话）。
- 写回页面的固定是**不挖舌孔族**的赢家（与「核算整线」里两族并列时的选择一致）；挖舌孔族的赢家
  打上「解法：挖舌孔」标签（沿用 R32 `TagFamily` 同一个写法，`ShapeRowText` 已经认这个标记）进
  「搜形状结果 ▾」，工程师选它才写回。
- 不是「两个都算」时只跑当前①页选的那一族——行为与改之前**逐位相同**。
- 输出框按族分段（`=== 第 N 族（不挖舌孔／挖舌孔）===`），两族都跑完后加一段「两族并列（各自最
  轻可行，不比重量）」小结，呼应 R32 「核算整线」两族并列时的表达方式。
- 进度条：`_prog.Maximum` 的初始估计在「两个都算」时整体翻倍（两族各跑一遍），后续的动态追加
  （二分/黄金分割/批次）仍然是「整批一次加」，不逐候选累加；状态文字带「第 1 族（不挖舌孔）／
  第 2 族（挖舌孔）」前缀，工程师能看出现在跑到哪一族。

线程安全：⑥⑦两段并发走的仍然是 R36 的 `ShapeBatchEval.RunAsync`；`allowCuts` 现在是
`SearchOneFamilyAsync` 的普通 `bool` 形参（调用时在 UI 线程按值捕获），线程池里的 `solveOne`
lambda 直接用它，不再有「跨线程读 ComboBox」这条路——`FamilyAllowsCuts`/`_tabTaper.Checked` 这
类活控件属性只在批前的 UI 线程同步段落里读一次，取成局部值再带进批处理，沿用 R36 合入时定下的
写法与注释。③④⑤⑧（不动点迭代/二分/黄金分割/精算）算法一行未动。

## 不覆盖

- 没有跑一次「默认轮数」的真实 `--searchshape`（几十分钟量级、答案有意义的那种）去实测锥形/孔族
  在真实案例上具体省了多少铂——本次门验的是「接线对不对」（并行、锥形、两族都被走到，且逐位可
  信），不是「这一档现场案例改锥形能省几克」。工程师要看具体数字，需要自己在真实档案上跑一趟。
- 两族各自的细网格精算（⑧「精算胜出形状」）目前都会各跑一次（不只是不挖舌孔那族），成本上等于
  把搜形状的总预算翻倍——这是「两族各跑一遍完整搜索」题面本身要求的（用户「一次搜完」的目标），
  不是遗漏，但没有额外做「先都用导航网格比一轮、赢面明显的那族才精算」这类省成本的优化，如果现
  场发现两族搜索的总时长不可接受，需要再单独决策要不要加这层筛选。
- `--searchshape`（不带 quick，默认轮数）与 `--repro` 里没有加锥形/孔族的联调断言——只在
  `quick` 模式补了，因为那是走查里唯一「分钟级、专门验接线」的入口；默认轮数模式本来就是「验答
  案好不好」，不该在里面加新的接线断言（会让人分不清超时到底是慢还是接线错）。
- HANDOVER.md 里另外几处提到「锥形」「孔族」的历史行（R31/R32 那两行）没有改写——那两行记的是
  当时做到哪一步的历史事实，本次是在它们的基础上继续往前做，不是订正它们。
