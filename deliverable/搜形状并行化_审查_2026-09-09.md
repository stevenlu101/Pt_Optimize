## 0. 先验前提：「各形状的解互不依赖」这句话只对了一半

任务描述里「各形状的解互不依赖，想并行」是审查的出发点，但读完 `SearchShapeAsync` 全文（`UI/LineDesignPage.cs:2836-3187`）
之后，这个前提**只在「一轮之内」成立**，跨轮不成立——搜索本身是一个自适应算法，下一个探针点由上一个探针点的结果决定：

| 阶段 | 代码位置 | 决策依据 | 是否独立 |
|---|---|---|---|
| ① 当前页形状（基准点） | `2921-2928` | 无 | 单点，与其余无关 |
| ② 最大盘径试探（拿板厚） | `2953-2958` | 无 | 单点 |
| ③ 盘径下界不动点迭代（≤3 次） | `2961-3037` | **上一次**解出的板厚 → `⑥` 闭式下界 | 严格顺序，逐次依赖 |
| ④ 二分定可行区间（≤3 步） | `2988-2998` | 上一探针可行/不可行 | 严格顺序，经典二分 |
| ⑤ 黄金分割找最轻点（4 点） | `3015-3033` | 累积 `rows` 定区间收缩方向 | 严格顺序，经典黄金分割 |
| ⑥ 剩余舌宽比例 | `3040-3045` | 只依赖已定的 `Rbest` | **本轮内互相独立**（≤2 点） |
| ⑦ 邻域探索（每轮≤6 轮） | `3066-3121` | 本轮 4 个邻点只依赖**上一轮**最优点；下一轮又依赖本轮结果 | **轮内 4 点互相独立**，轮间严格顺序 |
| ⑧ 胜出形状精算（细网格，1 次） | `3134-3149` | 上面全部收敛后的赢家 | 单点 |

真正满足「解互不依赖、可批量并行」的只有 ⑥（≤2 点/批，一次）与 ⑦（**恰好 4 个邻点**：
`ShapeSearchPlan.Neighbours` 固定返回 `(R±step, hw 的 up/down)` 四元组，`Core/ShapeSearchPlan.cs:92-104`）；
③④⑤是教科书式的定点迭代/二分/黄金分割，**下一探针的坐标要用上一探针的结果算**，结构上不可并行，
除非把算法本身换掉（那是另一件事，见第 5 节末尾）。

⇒ **同一批可并行的候选数天生只有 2～4 个**，不是「6 小时的活可以摊到 N 个核上」。这决定了第 4 节的 N 值建议
不是「越大越好」，而是「批大小定了上限」。

## 2. `SolverResult`/`LineResult` 是否引用共享对象

**结论：不共享。** 证据链：

- `Solver.Solve` 入口先 `var d = geometry.Clone()`（`Core/Solver.cs:279`）——**不改调用方传入的 `DesignSpec` 原件**，
  `res.Design = d` 挂的是这个私有克隆（`343`）。
- `DesignSpec.Clone()`（`Core/DesignSpec.cs:308-345`）对每一个数组字段逐份 `.Clone()`——这本身是踩过坑之后补的：
  代码注释直接写着 2026-09-06 曾经漏拷 `SlotSpanDeg`/`TabHoleRMm`/`TabHoleAspect` 三个数组，
  导致某条测试改副本的孔径，**就地污染了 `DesignSpec.Builtin[0]` 这个 static 实例**（`320-329`）。
  现有反射测试 `Pt_Optimize.Tests/CloneCopiesEveryArrayTests.cs` 扫描 `DesignSpec` 每一个 `public` 数组字段，
  以后任何新加字段漏拷贝都会当场红——**这是点 2 结论成立的护栏，不是断言**。
- `DesignSpec.Plate(j, floorMm)`（`Core/DesignSpec.cs:383-398`）每次 `new FlangePlate {...}`，不缓存不复用。
- `LineResult`（`Core/LineRunner.cs:538-`）与 `SolverResult`（`Core/Solver.cs:1876-1913`）都是普通实例类，
  字段（`Trace`、`Notes`、`Checks`、`Segments`、`Flanges`……）全部实例级，每次 `Solve`/`Run` 各自 `new`。
  唯一的「共享」是数组默认值 `Array.Empty<T>()`——CLR 保证的不可变单例，长度恒 0，天然安全。
- `baseIn`（`DesignInputs _base`）在整条链路里全仓 `grep "baseIn\.\w+\s*=|\.Base\.\w+\s*="` **零命中**——
  求解期间只读，与 `_base` 单实例被所有并行 `Solve` 调用共享**不冲突**。这是隐性契约，不是类型系统强制的；
  第 4 节把它列进「必须守住但不必现在改」的清单。

## 3. UI 侧：哪些状态要改，取消令牌怎么传

`SearchShapeAsync`（`UI/LineDesignPage.cs:2763-3213`）目前是纯 `await` 串行：`EvalShape` 每次调用在
`await Task.Run(() => Solver.Solve(...), ct)`（`2889-2892`）之前的同步前缀、之后的收尾（`rows.Add`/`_prog`/`_out`）
全部只在 UI 线程执行——这是因为 WinForms 的 `SynchronizationContext` 会把 `await` 之后的续体自动封送回 UI 线程，
`Progress<string>` 的 `Report` 同理（内部用捕获的 `SynchronizationContext.Post`，本来就是线程安全的设计）。

| 状态 | 现状 | 并行后会怎样 | 要不要改 |
|---|---|---|---|
| `rows`（`List<...>`，`2836`） | 只在 `await Task.Run` 之后的续体里 `Add`（`2898`） | 若继续用 `await`+`Task.Run` 的模式（而不是裸 `Parallel.For`/`Thread`），续体仍会被封送回 UI 线程**串行执行**，`rows.Add` 不会真并发——但这依赖「没人加 `ConfigureAwait(false)`、没人绕开 `Task.Run` 直接起线程碰 UI」这个隐性约定 | 不改代码逻辑，但要**新增一条测试/断言**钉住这个约定（例如在 `rows.Add` 前 `Debug.Assert(!InvokeRequired)` 当哨兵） |
| `done`/`baseDone`（`2861`,`2873`,`2894`） | `baseDone = done` 在 `await` **之前**取值，`done = baseDone + screenRounds` 在**之后**写回 | 多个 `EvalShape` 并发在飞时，后发起的调用会在先发起的还没写回 `done` 时就已经把 `baseDone` 读成旧值——**不是数据竞争（写回仍在 UI 线程串行），是逻辑错误**：进度条计数会不单调、可能倒退 | **必须改**：不要用「起点快照 + 结束时加总」的手工计数，改成用 `Interlocked.Increment` 累加已完成数，或者直接用 `rows.Count`/已完成 `Task` 数推进度 |
| `_prog.Value`/`_prog.Maximum`（多处） | 只在 UI 线程续体里改 | 同 `rows`——安全前提同上；`_prog.Maximum += screenRounds` 这种散落的自增在批量并行（一次派发 4 个邻点）时要一次性加完整批，不能在循环里边发边加（否则中途读到的 `Maximum` 是不完整的） | 建议改成：先算好本批总量再一次赋值，不要在批内累加 |
| `_out`（`RichTextBox`）/`TextFmt._rawText,_writing` | 同上，UI 线程独占 | 同上——`TextFmt.cs:428` 自己写明「只在 UI 线程上进出，不需要加锁」，这句话是并行化的硬约束，不是可选项 | 不改，但严禁任何方案把 `Solver.Solve` 之外的日志/结果处理挪到非 UI 线程直接调 `_out.AppendText` |
| 取消令牌 `ct`（`_cts.Token`，`2773-2774`） | 单个 `CancellationTokenSource`，`ct` 值类型直接传进每次 `Solver.Solve(..., ct)` | `CancellationToken` 本身按设计可安全地被多线程同时读/注册回调，N 个并行 `Solve` 共享同一个 `ct` **没有问题**；取消后 `Solver.Solve` 内部 `cancel.ThrowIfCancellationRequested()`（`Core/Solver.cs:405` 等多处）各自抛出，`Task.WhenAll` 会在全部完成/取消后统一冒出异常 | 不改，符合任务要求「随时可以点取消，已经算完的形状结果不会丢」（`2828`）——并行时要确认这句话在**批未完**时取消也成立（已完成的批内成员的结果要保留） |
| `PageToDesignSpec()`（`2867`）读 `_wall`/`_base` 等控件 | 每次 `EvalShape` 调用同步前缀里读一次 | 只要仍在 UI 线程发起（`await Task.WhenAll` 之前的 `Select`/循环体在 UI 线程跑完同步前缀），这段读取本来就互不冲突 | 不改 |

## 4. 方案：同进程 Parallel 还是多进程

**推荐：同进程、限并发（`Task.WhenAll` / `SemaphoreSlim` 限流），不建议多进程。**

理由：

1. 第 1、2 节的审查结论是——`Solver.Solve` 深处唯一真正**非线程安全且会被搜形状碰到**的共享物是 0 个
   （`_tfCache` 因 `_srcAnalytic.Checked` 强制而不可达）；其余全部是「只读」或「只在 UI 线程碰」。
   多进程要解决的正是「共享内存里有脏东西」，而这里**审出来基本没有**——多进程买不到额外的安全边际。
2. 多进程的代价是实打实的：`DesignSpec`/`DesignInputs`/`LineCase` 要能整体序列化传给子进程，
   `SolverResult`/`LineResult`（含 `Trace: List<string>`、`Checks: ConstraintOut[]`、嵌套 `SegmentOut[]`/`FlangeOut[]`）
   要能整体反序列化传回来——这些类型目前没有为跨进程设计（`SolverResult.Progress` 字段甚至是 `IProgress<string>` 委托，
   根本没法过序列化边界），要么裁一份「结果 DTO」专门给子进程用，要么放弃搜索过程中的细粒度进度汇报。
   这是一次不小的新增面，而不是「把 `Solve()` 换成子进程调用」这么简单。
3. 瓶颈是 CPU，不是内存/隔离性（见下面实测）：单形状 screening 求解全程吃满 1 个逻辑核、内存峰值 ~90 MB——
   进程隔离不会让 CPU 竞争消失，只是把「一个进程里 N 个线程抢核」换成「N 个进程抢核」，效果一样，多的只是进程间通信开销。

**实测（本次审查跑的，不是估的）**：Release 编译后，`Pt_Optimize.exe --cli --solve --wall 0.8`
（即单个形状、导航网格、无 `--fine`——与 `EvalShape` 的粗筛调用同一条路径：`ScreenCoarseMm`、无 `FineMm`）
后台跑了约 8 分钟，每 20~25 秒采样一次 `Get-Process`：

| 指标 | 采样范围 | 结论 |
|---|---|---|
| 工作集 WorkingSet | 70.3–78.0 MB | 稳定，无增长趋势 |
| 峰值工作集 PeakWorkingSet | **88.8 MB**（8 分钟内触顶后不再涨） | 单形状内存峰值 ≈ 90 MB |
| 私有内存 PrivateMemory | 36.5–44.6 MB | 同上 |
| CPU 时间增量 | 约 20~25 s／20~25 s 采样间隔 | **持续吃满 ~1 个逻辑核**，无迹象证明内部有多线程并行 |
| 线程数 | 4~8（含 GC/终结器/线程池待命线程） | 不是「求解本身开了很多工作线程」 |

机器本身 20 逻辑核 / 31.6 GB RAM（与 `Program.cs:6328` 注释「20 核的机器」一致，同一台）。
⇒ **内存完全不是约束**（N=20 也只占 ~1.8 GB）；**CPU 核数才是硬约束**，且比 CPU 核数更紧的是第 0 节说的
「批大小」——邻域探索每轮天生只有 4 个独立候选，舌宽比例批最多 2 个。

**N 值建议**：`N = min(本轮候选数（≤4）, Environment.ProcessorCount − 2)`。
工程师工作站核数通常远小于本仓开发机的 20 核（常见 8～16 核），但即使核数宽裕，**批大小 4 也封了顶**——
开大 `N` 换不来更多并发,除非把③④⑤（不动点/二分/黄金分割）也改成「一批多点」的算法，
那是**改算法**，会改变收敛路径，需要单独决策，不在本次「只并行、结果逐位不变」的范围内。

**必须先修的共享状态清单（按风险排序）**：

| 优先级 | 项 | 位置 | 动作 | 工作量 |
|---|---|---|---|---|
| P0 | `done`/`baseDone` 进度计数逻辑错误 | `UI/LineDesignPage.cs:2861,2873,2894` | 换成 `Interlocked` 累加或按 `rows.Count` 推导 | ~10 行 |
| P0 | 批次派发方式必须保持「`await`+`Task.Run`，不得 `ConfigureAwait(false)`/裸线程」 | `UI/LineDesignPage.cs:2845-2908`（`EvalShape`） | 不改现有结构，仅在批处把 `foreach await EvalShape` 换成 `await Task.WhenAll(批.Select(EvalShape))`；新增哨兵断言防回归 | ~20-30 行改动 + 1 个断言 |
| P1 | `Geometry3dm._tfCache` 无锁 Dictionary | `Core/Geometry3dm.cs:462` | 当前不可达，建议顺手换成 `ConcurrentDictionary` 做防御性加固（成本极低） | 1 行 |
| P2 | `_prog.Maximum` 批内多次累加 | `UI/LineDesignPage.cs:2975,2994,3025,3095` | 改成批前一次性加总 | ~5 行 |
| P3 | 搜索期间用户触发 `DesignSpec.Reload()` 的并发窗口 | `Core/DesignSpec.cs:1042-1048` | 确认/补充：搜索期间禁用一切会触发 `Reload()` 的控件（目前只锁了 `_btnRun/_btnAuto/_btnRepro`，`2776`） | 需要巡查一遍页面上「载入/另存设计记录」的按钮是否已被这条链间接挡住 |

**验收门写法**：

1. **逐位相同**：固定一组形状网格（沿用 `SearchDiscs={25,30,35}` × `SearchWFrac={0.75,1.00}`）与固定段数
   （3 段，归档基准），并行改造前后各跑一次完整 `SearchShapeAsync`，对比 `_out` 最终文本、`rows` 的
   `(mass, ok, msg)` 三元组集合、写回控件的 `_discD/_tabW/_tabLen/_tPlate[]`——要求**完全一致**（不是「数值接近」）。
   因为 ③④⑤ 阶段本身保持串行，唯一变的是⑥⑦阶段的**派发方式**而非**决策逻辑**，逐位相同是可达的目标，不是奢望。
2. **墙钟下降**：同一组形状，记录并行改造前后 `SearchShapeAsync` 从点击到完成的总耗时（复用页面已有的
   `clock`/`Note`，`2814-2820`）——因为只有⑥⑦两段真并行，预期降幅是「⑦阶段 4 点变 1 批」带来的，
   不是整体除以 N；下降幅度应与「⑦阶段总调用次数 / 4」这个理论值对得上，对不上要能解释差在哪（例如某轮候选被
   `Worth` 提前滤掉、批内有形状早退）。

## 5. 改动量与风险估算

| 改动 | 文件 | 预估行数 | 风险 |
|---|---|---|---|
| 批处派发改 `Task.WhenAll`（⑥⑦两处循环） | `UI/LineDesignPage.cs` | 改 ~30-50 行（`3040-3045` 舌宽比例批、`3066-3121` 邻域批），新增 1 个并发度限流辅助方法 ~15 行 | 中——核心逻辑（谁赢、何时收缩步长）不动，只动"怎么发起 4 次调用"；主要风险在**收尾聚合顺序**：现在 `rows` 的追加顺序是发起顺序，并行后是完成顺序，若下游有任何地方依赖 `rows` 的**顺序**（现读到的代码里没有找到——`BestMass()`/`OrderBy(mass)` 都与顺序无关），改了也不影响逐位相同 |
| 修 `done`/`baseDone` 计数 | `UI/LineDesignPage.cs` | ~10-15 行 | 低——纯 UI 展示量，不影响求解结果 |
| `_tfCache` 换 `ConcurrentDictionary` | `Core/Geometry3dm.cs` | 1 行 + `using` | 极低——防御性加固，即使不改也不影响本次任务（不可达） |
| 新增哨兵测试（UI 线程断言 + `DesignInputs` 不写反射门） | `Pt_Optimize.Tests/` 新文件 | ~60-80 行 | 低——纯新增，仿照仓库已有的 `CloneCopiesEveryArrayTests` 套路 |
| 逐位相同验收对拍（跑并行前后两份 `SearchShapeAsync` 输出并 diff） | 手工/脚本，不一定要进代码库 | 视做法而定 | 中——这是**验证工作量**而非**代码工作量**：一次对拍要跑两趟完整搜索（各 20-30 分钟 × 若干形状），比代码改动本身更耗时间 |

**总量级**：核心并行化代码改动约 **60-100 行**（集中在 `LineDesignPage.cs` 两处循环 + 一个限流辅助方法），
配套测试约 **60-80 行**，`Core/` 侧仅 1 行防御性加固——改动面小，风险集中在"验收门要真正跑两趟对拍"而不是代码本身。

**没有覆盖到、留给后续决策的**：把③④⑤（不动点迭代/二分/黄金分割）也改成批量并行需要换算法（例如一次性
评估多个候选半径再选，类似网格搜索），这会改变探针序列、可能改变收敛到的具体形状（哪怕最终质量目标相近），
超出"只改执行方式、结果逐位不变"的验收门，需要用户单独拍板是否接受"更快但探针路径不同"。
